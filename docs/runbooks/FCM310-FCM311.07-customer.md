# Runbook – FCM310 / FCM311.07 NetSuite Customer extract (AWS)

ServiceNow change: **CHG0032633**

Replaces the Boomi process `FCM311.07-NS.CUST.BOOMI-CHILD.TRG` (called by `FCM310-BOOMI.PROC.BOOMI-PARENT.SCH`
through FCM311 for the `CUSTOMERS` driver). Only the Customer driver moves to AWS; every other FCM310 driver keeps
running in Boomi.

Infrastructure: `terraform/infrastructure/customer.tf`. Names below use `<stage>` = `dev | qa | preprod | prod`.

## Architecture

```
EventBridge Scheduler  netsuite-etl-<stage>-fcm310-customer-{0430,0805,daytime}   (UTC-7)
  └─► Step Functions   netsuite-etl-<stage>-fcm310-customer                      (FCM310, Customer driver only)
        └─► Glue job   netsuite-etl-<stage>-fcm311-07-customer-extract           (FCM311.07, Python shell)
              ├─ Secrets Manager  <stage>/netsuite/suiteql/secret               NetSuite TBA credentials (SuiteQL REST)
              ├─ SSM parameter    /netsuite-etl/<stage>/fcm311-07/customer/last-successful-run-date   (UTC)
              └─ S3  s3://<snowflake bucket>/SNOWPIPE/NETSUITE/CUSTOMERS/NS_CUSTOMERS_yyyyMMdd_HHmmss.csv
                    └─► Snowpipe ─► Snowflake
Failures (FAILED / TIMED_OUT / ABORTED) ─► EventBridge rule ─► SNS netsuite-etl-<stage>-fcm310-customer-alerts
```

### Delta logic and why a retry never skips records

1. The job captures `run_start` (UTC) **before** querying NetSuite.
2. It extracts `lastmodifieddate >= LSRD - customer_overlap_minutes` (keyset pagination on `id`, 1000 rows per call).
3. It writes one file to S3 (only if there are records).
4. Only then it sets the LSRD to `run_start`.

If anything fails before step 4, the LSRD is unchanged and the next run (the automatic retry 5 minutes later, or the
next schedule) re-reads the same window. Overlapping triggers are skipped (`max_concurrent_runs = 1`) and the
running extract covers them. The SSM parameter is created by the job, not by Terraform, so an apply never moves it.

## Credentials

* Secret `<stage>/netsuite/suiteql/secret`, owned by operations (the Terraform plan fails if it does not exist).
  Keys: `BASE_URL` (full `.../services/rest/query/v1/suiteql` URL), `ACCOUNT_ID`, `CONSUMER_KEY`,
  `CONSUMER_SECRET`, `TOKEN_ID`, `TOKEN_SECRET`.
* Signature: OAuth 1.0 TBA, **HMAC-SHA256**.
* The NetSuite role behind the token needs *SuiteAnalytics Workbook*, *REST Web Services*, *Log in using Access
  Tokens* and *Lists > Customers (View)*.
* **Rotation:** create the new token in NetSuite, update `TOKEN_ID`/`TOKEN_SECRET` in the secret, run a manual
  execution (see *Replay*) and revoke the old token once it succeeds. No deploy is needed.
* `customer_netsuite_timezone` (default `America/Los_Angeles`) **must match the timezone preference of the NetSuite
  user that owns the token**: SuiteQL interprets and returns dates in that timezone and the job converts to/from UTC
  with it.

## Deploy

Through GitHub Actions (`Deploy` workflow, DEV → QA → PREPROD → PROD) or by hand with the same commands:

```bash
make plan STAGE=dev
make apply STAGE=dev
make apply STAGE=prod TFSTATE_BUCKET=platform-infra-terraform-state-prod
```

Per-stage settings live in `terraform/envs/<stage>.tfvars`: `customer_alert_email` (support DL; confirm the SNS
subscription email after the apply) and `customer_schedule_enabled` (keep `false` until cutover).

## Cutover (Boomi → AWS)

1. Deploy the stage with `customer_schedule_enabled = false`.
2. In Boomi, read FCM311.07's Last Successful Run Date (Atom Management → Deployed Processes → Edit Process
   Properties). It is shown in **your local timezone**; convert it to UTC.
3. In the FCM310 Cross Reference table set `PROCESS_FLAG = false` for the `CUSTOMERS` driver (the other drivers stay
   `true`). Wait until any in-flight FCM310 execution finishes.
4. Run the first AWS execution from that LSRD:
   ```bash
   aws stepfunctions start-execution --state-machine-arn <customer_state_machine_arn> --input '{"fromDate":"2026-10-23T11:30:00Z"}'
   ```
5. Validate (next section). Then set `customer_schedule_enabled = true` in the stage's tfvars and deploy.
6. Watch five consecutive scheduled executions (Step Functions console → `netsuite-etl-<stage>-fcm310-customer`):
   all `SUCCEEDED`, no timeouts, no manual intervention. FCM and BI sign off.

## Validation

* Job log (CloudWatch → `/aws-glue/python-jobs/output`, filter by run id) prints the window, records per page, total
  and the S3 key. Metric `NetSuiteETL / RecordsExtracted` (dimension `JobName`) has the count per run.
* NetSuite count for the same window (SuiteQL, in the token user's timezone):
  ```sql
  SELECT COUNT(*) FROM Customer WHERE lastmodifieddate >= TO_DATE('2026-10-23 04:30:00', 'YYYY-MM-DD HH24:MI:SS')
  ```
* Snowflake: count and IDs loaded from the file must match the job total and the NetSuite count:
  ```sql
  SELECT COUNT(*), COUNT(DISTINCT ID), COUNT(TOPLEVELPARENT)
  FROM <customer table>
  WHERE METADATA$FILENAME = 'SNOWPIPE/NETSUITE/CUSTOMERS/NS_CUSTOMERS_yyyyMMdd_HHmmss.csv';  -- or the load column used by the pipe
  ```
* Compare one AWS file with one Boomi file for the same customers (column order, quoting, `T`/`F`, empty values,
  numbers and dates). The date/datetime split is in `DATETIME_COLUMNS` / `DATE_COLUMNS` of the script; adjust there
  if BI finds a column with the wrong treatment.

## Replay / backfill

Start an execution with `fromDate` (ISO-8601 UTC, or Boomi's `yyyyMMdd HHmmss` read as UTC). The extract goes from
that date to *now* and then moves the LSRD to the run start, so a replay never leaves a gap:

```bash
aws stepfunctions start-execution --state-machine-arn <customer_state_machine_arn> --input '{"fromDate":"20261020 000000"}'
```

To just re-run from the stored LSRD (e.g. after an alert): start it with `{}`.

To move the LSRD without running:
`aws ssm put-parameter --name /netsuite-etl/<stage>/fcm311-07/customer/last-successful-run-date --value 2026-10-23T11:30:00Z --overwrite`.

A `fromDate` later than the stored LSRD skips the records in between (the job logs a warning).

## Monitoring

* SNS `netsuite-etl-<stage>-fcm310-customer-alerts` receives a message for every FAILED / TIMED_OUT / ABORTED
  execution. The message includes the execution ARN; the failing state shows the Glue run id and error.
* A Glue failure is retried once automatically after 5 minutes before the alert.
* Glue job timeout: `customer_job_timeout_minutes` (60). Unlike Boomi, a timeout still leaves the full log in
  CloudWatch.

## Troubleshooting

| Symptom | Action |
|---|---|
| `No Last Successful Run Date found` | First run without `fromDate`. Start it with `fromDate` (Cutover step 4). |
| `SuiteQL error 401` / `INVALID_LOGIN` | Token revoked/expired or wrong secret values; check the NetSuite *Login Audit Trail*. |
| `SuiteQL error 400` | Column not available to the role or invalid SuiteQL; the NetSuite message is in the log. |
| HTTP 429 / 5xx | Retried with backoff (6 attempts). Persistent: NetSuite concurrency limit shared with other integrations. |
| `SkippedPreviousRunStillActive` | Previous run still running; no action. Repeated: check job duration / timeout. |
| Data missing in Snowflake but job succeeded | Check the file in S3 and the Snowpipe `COPY_HISTORY` for that file. |

## Rollback (to Boomi)

1. Set `customer_schedule_enabled = false` and deploy (or, to act at once, disable the three
   `netsuite-etl-<stage>-fcm310-customer-*` schedules in the EventBridge Scheduler console and follow up with the
   tfvars change so the next apply does not re-enable them).
2. Read the AWS LSRD: `aws ssm get-parameter --name /netsuite-etl/<stage>/fcm311-07/customer/last-successful-run-date` (UTC).
3. In Boomi set FCM311.07's Last Successful Run Date to that value **converted to your local timezone** (Boomi
   converts it to PST and then UTC).
4. Set `PROCESS_FLAG = true` for `CUSTOMERS` in the FCM310 Cross Reference table.
5. Run FCM310 once manually and confirm the Customer file reaches Snowflake.

The stack can stay deployed while disabled. Test this rollback in dev/QA before the prod cutover and record the
result in CHG0032633.
